## Problem

This repo vendors Newton as a **forked submodule** (`abhinavj98/newton`), currently detached at:

```text
912c3bd8  2026-07-01  newton 1.4.0.dev0
```

That SHA is **not** upstream. It is two product commits on top of an older upstream merge:

| Commit | What it is |
| --- | --- |
| `ab6da1cd` | Public `SolverVBD.gather_joint_wrench_child_com` + `gather_joint_wrench_child_at_com_kernel` wrapping `evaluate_joint_force_hessian` |
| `912c3bd8` | Same kernel after control rename `joint_target_pos/vel` → `joint_target_q/qd` |

Upstream `v1.5.0` and `upstream/main` **do not contain** that method. `apple_pick_sim` calls it on every coupled substep (proxy coupling, batched obs, fruiting force readout). A naive `git submodule update` to the tag would compile Newton and then fail at runtime in the wrench path.

Separately, in-process CMA / `stress_plant_rebuild_loop.py` dies with delayed host-heap corruption (SIGSEGV / poisoned `code`/`function` objects). The leading match is OpenUSD `LoadUsdPhysicsFromRange`, **fixed in usd-core 26.5** (newton issues #3655 / #3293). This worktree already has an **uncommitted** Newton `pyproject.toml` bump to `usd-core>=26.5,<27` and `uv.lock` resolved **usd-core 26.8**. Stock Newton 1.5.0 still caps `<26.5`. Updating “to latest stable” without the overlay would move **backward** on the crash hypothesis.

## Goal

1. Run this project on **Newton 1.5.0** plus a **minimal, documented fork overlay**.
2. Keep the gather-wrench API **behavior-compatible** with today (same public method, same `(N,3)` force/torque numpy; device kernel in `apple_pick_sim/vbd_fixed_joint_wrenches.py` still launches the internal kernel).
3. Keep **usd-core ≥ 26.5** so the OpenUSD fix is not lost.
4. Migrate apple-pick call sites that 1.5.0 **deletes** (`joint_target_pos` / `joint_target_vel`, `SolverNotifyFlags`).
5. After the bump, **measure** rebuild+step crash rate. Do not treat a single clean run as proof.

## Why this slice (and why not `upstream/main`)

Newton 1.5.0 is the first tagged release after this pin. It is the right review boundary: Warp ≥ 1.16.0, MuJoCo 3.11, USD importer changes, VBD cable four-slot layout, removed deprecated control aliases.

`upstream/main` as of 2026-08-27 is ~105 commits further (implicit actuation, Kamino joint friction, hydroelastic, `ControllerJointImpedance` rewrite). Those are unreleased and not required to test the usd-core / SIGSEGV hypothesis. Absorb them in a later bump once 1.5.0 is green.

## Fork overlay (must survive the merge)

### 1. `gather_joint_wrench_child_com`

**Who uses it (apple_pick_sim, not gym):**

| Caller | Role |
| --- | --- |
| `apple_pick_sim/vbd_fixed_joint_wrenches.py` | Host API + device kernel launch (`newton._src…gather_joint_wrench_child_at_com_kernel`) |
| `apple_pick_sim/coupled_fruiting/proxy_coupling.py` | Harvest / weld wrench on GPU |
| `apple_pick_sim/batched_obs.py` | Batched force features |
| `apple_pick_sim/fruiting_system/scene.py` | `measure_fruiting_forces` |

**Rebase requirement (not a copy-paste of `912c3bd8`):** on 1.5.0, `evaluate_joint_force_hessian` gained two cable-rest arrays **before** `joint_qd_start`:

```text
joint_cable_rest_kb_local: wp.array[wp.vec3]
joint_cable_rest_twist: wp.array[float]
```

The fork kernel and both launch sites (Newton `SolverVBD.gather_joint_wrench_child_com` and `apple_pick_sim.vbd_fixed_joint_wrenches.gather_joint_wrench_child_com_device`) must pass those arrays. FIXED-joint queries still use LINEAR=0 / ANGULAR=1; the extra args are unused for that joint type but are required by the Warp signature.

Keep the Newton-side unittest `_gather_joint_wrench_child_com_finite_after_step` in `newton/newton/tests/test_solver_vbd.py`.

Do **not** try to delete the `newton._src` import in this slice. The device hot path already mirrors the public method; changing that is a later cleanup.

### 2. `usd-core>=26.5,<27`

Stock 1.5.0:

```text
usd-core>=25.5,<26.5   # EXCLUDES the OpenUSD 26.5 heap fix
```

Overlay:

```text
usd-core>=26.5,<27 ; platform_machine != 'aarch64' and python_version < '3.14'
```

This pin is already in the dirty `newton/pyproject.toml` of this worktree and in parent `uv.lock` (26.8). After merging 1.5.0 it will be overwritten unless re-applied. Treat it as a **first-class fork commit**, not a local hack.

Optional belt-and-suspenders (already documented, not required to land the bump): `PXR_WORK_THREAD_LIMIT=1` before `pxr` import; `load_visual_shapes=False` is already in `build_fr3_robot_builder`.

### Already true on the current pin (do not retune for 1.5.0)

The current 1.4.0.dev0 CHANGELOG already includes VBD **absolute** damping (`kd` is physical, not Rayleigh `kd·ke`). Fruiting `stretch_damping` / `bend_damping` and `FRUITING_VBD_RIGID_JOINT_*_KD` were written against that. **Do not** apply `kd_new = kd_old · k` as part of this bump.

### Out of blast radius

Kamino, MPM, Style3D, `newton.controllers.ControllerJointImpedance`, tiled camera, hydroelastic — unused on the M4 CMA / coupled fruiting path.

Gym does not import `joint_target_pos` or `SolverNotifyFlags`. Gym tests that index `SolverVBD.JointSlot.LINEAR` / `ANGULAR` on **FIXED** support joints remain valid.

## SIGSEGV / in-process rebuild

**Hope:** Newton 1.5.0 + usd-core 26.5+ + existing `load_visual_shapes=False` reduces or eliminates delayed heap corruption when rebuilding and stepping `BatchedHeterogeneousCoupledSim`.

**What is already true in this worktree (before the bump):**

- Parent `uv.lock` has `usd-core==26.8`.
- Newton `pyproject.toml` is **dirty**: pin raised to `>=26.5,<27` (not in `912c3bd8`).
- FR3 import uses `load_visual_shapes=False`.
- Production CMA still defaults to **process-isolated** eval waves.

**What 1.5.0 does *not* do:**

- It does **not** raise the usd-core cap. Stock 1.5.0 would fight the 26.8 lock (`<26.5`).
- USD importer changes (visual vs collision split, static visuals) are relevant only if we start loading visuals again. Headless CMA should not.

**Acceptance for the crash hypothesis (not for the API bump):**

Use the protocol in `docs/in-process-rebuild-heap-corruption.md`: `--replay-steps` must be &gt; 0; compare **crash rates** over repeated trials, not one pass. Isolation remains the production default until the rate is actually lower.

If the rate does not drop, the overlay still has value (wrench API + 1.5.0 APIs). Do not revert the bump solely because SIGSEGV remains; file a Newton-only loop reproduction instead.

## Non-goals

- Upstream PR of `gather_joint_wrench_child_com` into `newton-physics/newton` (desirable later; not blocking).
- Pinning `upstream/main` / Newton 1.6.dev.
- Changing CMA phenotype, Sinkhorn bags, or `--no-isolated-eval-waves` default.
- Retuning Young's / support-\(k_p\) search boxes because of this bump.
- Rewriting `AppleModelBuilder` in `example_apple_stem.py` unless 1.5.0 `add_rod` breaks that example’s tests.

## Implementation approach (summary)

Work on a **sibling worktree** (this checkout is already `feature/real-replay-parallel-sysid`; do not pile the bump on `main`). Sequence:

1. On `abhinavj98/newton`: branch from current submodule SHA → merge tag `v1.5.0` → replay wrench commits against the new hessian signature → commit `usd-core>=26.5,<27`.
2. In the parent repo: point `newton/` at that fork SHA; `uv sync --extra gym --extra vic --extra dev`.
3. Apple-pick API migration (flags, joint targets, wrench kernel extra args) with tests first.
4. Fast pytest, then coupled smoke, then optional crash-rate harness.

Exact tasks: `docs/superpowers/plans/2026-08-27-newton-1.5-submodule-update.md`.

## Success criteria

**API bump (required):**

- Submodule is a descendant of `v1.5.0` plus overlay commits; `newton.__version__` reports `1.5.0` (or `1.5.0` + local version if the fork bumps it — prefer leaving version as 1.5.0 and documenting overlay in CHANGELOG).
- `SolverVBD.gather_joint_wrench_child_com` exists; `test_solver_vbd` gather test passes.
- `usd-core` in the lock is `>=26.5,<27`.
- No remaining `SolverNotifyFlags` or `.joint_target_pos.assign` in `apple_pick_sim/` / `apple_pick_gym/`.
- Fast sim tests and gym unit/CLI tests pass; `example_coupled_fruiting.py --viewer null --num-frames 60` and `verify_coupling.py` pass.

**Crash hypothesis (optional, reported separately):**

- Crash-rate table for `stress_plant_rebuild_loop.py --mode rebuild-replay` vs pre-bump baseline. A single survival is not success.
